## 0. 结论摘要

1. **官方软件的字段字典找到了**：`BIGBIG WON/config.xml` 里的 `<base_profile>` 用**属性名**列出了每个参数（`gyro_sens`/`h2v_ratio`/`resp_curve`/`deadzone_comp`/`select_curve`…），`DefaultConfig.ini` 里的数组则是**各机型默认 profile，数组下标 == 508B payload 偏移**（已用 `Rainbow3_508_0x39` 逐字节对齐校验）。
2. **`[319..343]` 不是"摇杆响应曲线区"**，而是 **motion（体感）块的 2 份额外副本**。真正的"响应曲线"参数是 `resp_curve`，就在 `[318]`。
3. **震动块 `[352..360]` 已解开**：4 个参数（左/右 × 下限/上限），每个占 2 字节（值重复一次）；`[360]` 是档位，且来源不是 profile，而是 `CProfileAdaptor` 实例字段 `this+12862`。
4. 真正"无人写、无人读"的区间收敛为：`[309..310]`、`[313..314]`、`[317]`、`[319..343]`、`[348]`、`[361..379]`。它们**只从默认模板来、只被原样回传**，官方软件不编辑。

## 8. 多机型 / 多版本：把"固件版本号"到底是什么说清楚

### 8.1 版本号不是"同一支手柄的固件号"

`DefaultConfig.ini` 里 19 条默认 profile 的命名规则是 `<机型>_<长度>_0x<版本>`：

| 版本 | 长度 | 官方机型（DefaultConfig.ini 前缀） | 说明 |
|---|---|---|---|
| 0x34 | 240 | Default | 最老一代 |
| 0x35 | 240 | Default / GALE / MAGE | 与 0x34 **布局完全相同**（见 8.2），仅版本号不同 |
| 0x36 | 280 | Default / GALE / MAGE / BLITZ2 / Aether / Rainbow3 / MSY01 / GALE2 | **7 个机型共用同一套协议** |
| 0x37 | 484 | Default / BLITZ2 | |
| 0x39 | 508 | Default / Rainbow3 | 本项目当前目标 |
| 0x60 | 335 | Default / GALE2 | |
| 0x61 | 456 | GALE2 | 构建器写法与其它版本差异最大 |

结论：**`0xNN` 是"协议/配置格式版本"，跟着产品代次走，不是某一支手柄的固件版本号。**

两条硬证据：
1. **同一机型出现在两个版本里** —— `Rainbow3_280_0x36` 与 `Rainbow3_508_0x39` 并存。同一款手柄能在两个协议版本下出现 → 版本号跟随**硬件/固件代次**，不是机型标识。
2. **同一版本被 7 个机型共用** —— 0x36/280 覆盖 GALE、MAGE、BLITZ2、Aether、Rainbow3、MSY01、GALE2。这些机型字节长度与偏移完全一致，只有默认值（死区、曲线、键位）不同。

所以"支持一款手柄"实际是"支持它的 (版本, 长度)"组合；19 条默认条目只对应 **6 种长度 / 7 个版本**。

### 8.2 各版本的偏移迁移表（已批量反编译自动抽取）

以**应用侧 profile 偏移为锚点**（`a2` 结构跨版本通用），抽取各 `Implant2PadSet_vNN` 里 `a3 + N = a2 + M` 的对应关系：

| 版本 | 长度 | `h2v_ratio` | `gyro_sens` | `resp_curve` | `deadzone_comp` | 键使能(dword) | 键槽区起点 |
|---|---|---|---|---|---|---|---|
| v34 | 240 | 45 | 46 | 48 | 68 | 81 | 112 |
| v35 | 240 | 45 | 46 | 48 | 68 | 81 | 112 |
| v36 | 280 | 87 | 88 | 90 | 84 | 116 | 152 |
| v37 | 484 | 291 | 292 | 294 | 288 | 320 | 356 |
| v39 | 508 | 315 | 316 | 318 | 312 | 344 | 380 |
| v60 | 335 | 111 | 112 | 114 | 108 | 140 | 207 |
| v61 | 456 | 间接传入（非直拷，未抽出） | | | | — | 328 |

规律（v36 及之后）：`h2v_ratio` = base，`gyro_sens` = base+1，`resp_curve` = base+3，`deadzone_comp` = base−3；键槽区固定为 `长度 − 128`，键使能固定为 `键槽起点 − 36`。
**v34/v35 例外**：`deadzone_comp` 在 68（不是 base−3），键使能在 81（不是 76），属早期布局。

分帧数也随之变化（59B/满块，末块取余）：

| 长度 | 240 | 280 | 335 | 456 | 484 | 508 |
|---|---|---|---|---|---|---|
| 帧数 | 5 | 5 | 6 | 8 | 9 | 9 |

当前 `chunks.js` 把 9 帧/508B 写死了，要支持其它版本必须参数化。

### 8.3 因此"一次发现 → 全部支持"是不成立的

| 层 | 是否跨版本通用 |
|---|---|
| 语义层（字段叫什么、什么含义、默认值） | 通用。`config.xml` 是全局字典，`gyro_sens/h2v_ratio/resp_curve/deadzone_comp` 各版本同名同义 |
| 布局层（字段在第几字节、多长） | 否：每个 (版本,长度) 一套表 |
| 分帧层（几帧、末块多长） | 否：随长度变 |
| 校验层（CRC-16/MODBUS @[0..1]） | 通用（已用官方默认数组 19 条交叉验证，见 8.4） |

要真正支持全系，还缺两块**只能靠真机**补的：① 版本探测（连上后如何判断对方是 0x36 还是 0x39 —— 长度可从回读帧数推断，但 0x34/0x35 同为 240 无法靠长度区分）；② 各版本写帧的 seq 数与末块长度是否符合 8.2 的推算（目前只在 508B 上验证过）。

### 8.4 顺带完成的校验交叉验证

`DefaultConfig.ini` 的每条默认数组**自带 `[0..1]`**，用 `crc16Modbus(payload[2..507])` 复算：

```
Rainbow3_508_0x39  payload[0..1]=147,103  计算=147,103  匹配
Default_508_0x39   payload[0..1]=147,103  计算=147,103  匹配
```

即**校验算法与"数组下标 == payload 偏移"这两条同时被官方默认配置反向验证**，不再只依赖单次抓包。

## 9. 真机实测记录（2026-11-15，2.4G 连接，VID 413D / PID 2104）

本节全部是**真机落盘数据**，不是抄录样本。工具：`bbw-protocol/tools/pad.mjs`（无头 HID CLI）。

### 9.1 通道打通

- 配置通道 `MI_02 / usagePage 0xFF7A` 在 2.4G 模式下同样存在（`MI_00` 是 XInput 游戏输入）
- 读：发 `a5 04 d6 7f` → 收满 9 帧 `a4 … d6`
- 写：9 帧 `a4 … d7` → **写后回读逐字节一致**，通道闭环成立
- 首次读回 CRC `b6 d0` 自洽，`header = 01 fc 00`（与 `DefaultConfig.ini` 真值一致，此前抄录样本里的 `fc 01` 确认是笔误）

### 9.2 设备不做范围钳位

对已知字段 `[5]`（左扳机死区低点）写 0/25/50/…/250，**全部原样读回**。

结论：**"参数范围"不是设备约束**。0..255 一律照收，量程限制只存在于官方 UI 层（滑块 min/max）与实际生效逻辑里。这意味着测语义必须看**物理行为**，不能靠读回值推测合法区间。

### 9.3 逐字节落盘性（探针 0x5A，单字节改动 + 读回）

| 区间 | 结果 |
|---|---|
| 309, 310, 313, 314, 317, 348 | **全部落盘** |
| 319..343（逐字节抽测）、349..351 | **全部落盘** |
| 361..376 | 落盘，但**字节序被反转**（见 9.4） |
| 377..379 | 落盘，原样保存 |

**推翻旧结论**：此前判定 `[309..310] / [319..343] / [348] / [361..379]` 为"无主字节（DLL 中 0 常量模板、读写路径均不引用）"。实测表明它们在设备端都是**真实可写可存的字段**，只是官方软件从不写它们（保持默认 0）。"官方不写" ≠ "字段不存在"。

### 9.4 `[361..376]` 的字节序陷阱

16 字节 = 4 组 uint32（361、365、369、373 各一组）。写入与读回**字节序相反**，且是 involution（每次写都翻转）：

```
写 361: 11 22 33 44 → 读回 44 33 22 11
写 361: 44 33 22 11 → 读回 11 22 33 44   ← 再翻一次
```

推论：**"读 → 改一个无关字段 → 写回"会把这 4 个 dword 翻转一次**。当前它们全 0（翻转后仍是 0，无害），但一旦官方软件写入非零值，现有 UI 保存路径（`serializeProfile(profile, from=read)`）就会静默破坏这 4 个字段。待真机确认语义后需要在写路径做反向补偿。

## 12. 摇杆处理链：径向死区 + 径向曲线（真机实测，第三轮）

### 12.1 完整模型

```js
r  = Math.hypot(lx, ly) / 32767 * 100            // 径向模长百分比
if (r <= dz) out = {x:0, y:0}
else {
  r1 = (r - dz) / (100 - dz) * 100               // 死区重映射到 0..100
  y  = piecewiseLinear(curve5Points, r1)         // 5 点分段线性，0..100
  k  = y / 100 * 32767 / r                       // 保持方向的比例因子
  out = {x: lx * k, y: ly * k}                   // 方向不变
}
```

**关键点：曲线是「径向响应曲线」，不是分轴曲线**。这与真实手柄的摇杆 gate（圆形/八角形
限位）语义一致 —— 用户调的是「推多远 → 输出多强」，方向由摇杆本身决定。

### 12.2 四组独立验证（同一固定输入：LX −75.5%、LY +33.1%，径向 r=82.1%）

| 曲线 y 值 (x=20/40/60/80/100) | 模型预测 | 实测 LX / LY | 实测模长 | 方向比 |
|---|---|---|---|---|
| `(100,100,0,0,0)` | y(82.1)=0 → 全归零 | **0 / 0** | 0 | — |
| `(0,0,100,100,100)` | y=100 → 满值 | −30035 / 13100 | 32766 | −2.293 |
| `(0,0,0,100,0)` | y=87 → 28507 | −27687 / 12092 | 30114 | −2.289 |
| `(0,0,0,0,100)` | y=13 → 4259 | −2142 / 936 | 2338 | −2.289 |
| 基线 `(20,24)…(100,100)` | y(82.1)=83.0 | −24681 / 10805 | 26942 | −2.284 |

**方向比全程 −2.28 ± 0.01** —— 向量方向严格保持，只有模长被缩放。
若为逐轴查表，`(100,100,0,0,0)` 时 Y（输入 33%，落在第 2 段）应输出满值，
实测却是 0，**直接否掉分轴模型**。

### 12.3 死区也是径向：`(r−dz)/(100−dz)` 精确成立

固定 r=82.1%，扫槽 0 的 `[off+2]`（`deadzone_center`，当前 0）：

| `[16]` | 实测 LX / LY | 模长 | 占满量程 | 公式预测 |
|---|---|---|---|---|
| 0 | −24681 / 10805 | 26942 | 82.2% | 82.2 |
| 20 | −23329 / 10220 | 25475 | 77.7% | 77.8 |
| 40 | −21071 / 9239 | 23009 | 70.2% | 70.3 |
| 60 | −16602 / 7279 | 18135 | 55.3% | 55.5 |
| 70 | −12132 / 5319 | 13248 | 40.4% | 40.7 |
| 78 | −5239 / 2295 | 5719 | 17.5% | 17.9 |
| 85 | **0 / 0** | 0 | 0 | r<dz → 0 |

反解每档的 r：82.16 / 82.12 / 82.12 / 82.12 / 81.85 —— **一致**。
方向比全程 −2.28，**死区同样只缩放模长，不扭曲方向**。

注意：修正 §11.5：上一版说「压缩比例不符合 `(x−dz)/(100−dz)`」，是因为当时拿单轴 `LX`
当输入。改用径向模长后公式**完全吻合**。

### 12.4 校正 §11.2 的输出量纲

上一版写的 `输出 = y × 303.44` 只是**在特定斜向位置下 X 分量的数值**，不是通用系数。
正确表述：

```
输出向量模长 = y/100 × 32767          （y=100 → 满量程 32767）
X 分量 = 模长 × (lx / r)              （故斜向时 X 分量 < 32767）
```

验证：上一轮位置 X:Y = 0.923:0.385，y=100 时 X 分量 = 0.923×32767 = **30250**，
与当时实测 30344 差 0.3% —— 原「303.44/点」正是 `327.67 × 0.926` 的巧合分解。


### 12.5 低于首个断点：从原点线性插值（实测）

把 x 断点整体抬到 90 以上（`x=90,92,94,96,100`，`y=50,50,50,50,100`），
当前径向 r=81.9% 就落在**首个断点之前**：

| 假设 | 预测输出 | 实测 |
|---|---|---|
| 钳位到首点输出 | 50% | — |
| **从 (0,0) 线性插值** | **45.6%** | **45.0%（模长 14754）** |

→ 采用 `out = y0 × r1 / x0`。对照补丁 `y=0,0,0,0,100` 输出 0，同样符合。

### 12.6 模型的 ~1% 系统性偏差（已知，不影响语义）

用默认曲线反解各档死区对应的径向 r：**81.2 / 81.2 / 81.2 / 81.2 / 81.3**（五档完全一致），
而 `hypot(lx,ly)/32767×100` = **81.9**。差 0.9%。

结论：固件使用的「径向百分比」比几何模长小约 0.9%，
推测原始 HID 轴与 XInput 输出之间存在微小比例差（XInput 侧可能有缩放或四舍五入）。
语义（径向、方向不变、公式形状）不受影响，**数值复现时需接受 ±1.5% 误差**。

| UI 曲线编辑器 | 应标为「**摇杆响应曲线（径向）**」，横轴是"推杆距离"而非单一轴 |
| UI 死区滑块 | `deadzone_center` 是**径向**死区半径，不是单轴死区 |
| 曲线输出上限 | 必须 clamp 到 **0..100**，越界（如 127）会导致整条曲线被静默丢弃（§11.3） |
| 曲线槽 2..5 | 本机型（413D:2104）不生效，保留透传 |
| 代码 | `applyJoystickCurve()` 已实现该模型，测试锁定 9 条（`test/joystick-radial.test.js`） |

## 13. `[12]` / `[13]` / `[311]` 与体感开关（第四轮真机实测）

测试条件：手柄立起、四轴全被皮筋固定（LX +44.8%、LY −18.3%、RX −56.6%、RY +14.2%），
`settle=800ms`、采样 420ms、每轮末复测基线（漂移 <62 计数）。

### 13.1 `[13]` = 轴反转位域（**已闭死**）

| 位 | 值 | 实测效果 | 判定 |
|---|---|---|---|
| bit0 | 1 | LX +14652 → **−14652** | 左摇杆 X 反转 |
| bit1 | 2 | LY −5936 → **+5936** | 左摇杆 Y 反转 |
| bit4 | 16 | RX −18547 → **+18551** | 右摇杆 X 反转 |
| bit5 | 32 | RY +4639 → **−4642** | 右摇杆 Y 反转 |
| bit2/3/6/7 | 4/8/64/128 | 四轴零变化（≤23 计数） | 未用，或仅影响体感 |

与 `config.xml` 完全对应：`joystick_left` / `joystick_right` 各带
`xaxis_reversal` / `yaxis_reversal`，共 4 个位。

注意：修正 §10.5：早先记的「`[13]=1 → LX 归零`、`[13]=2 → LY 符号翻转`」是在 **150ms 等待**下取的，
属于后来被证伪的过渡态数据。真值是**符号反转**，不是归零。位布局是 bit0/1 左、bit4/5 右（**不是** bit0..3 连续）。

### 13.2 `[12]` 八个位全部无效果

当前真机 `[12]=0x46`（出厂 0x66）。逐位写 1/2/4/8/16/32/64/128，四轴变化 40–74 计数，
全在漂移范围内。**`[12]` 不控制摇杆**（推测属于 turbo / 按键映射开关一类）。

### 13.3 `[311]` 单独写无效，原因在反编译里

对 `Implant2PadSet_v39` 的反汇编（第 70–95 行）给出：

```c
a3[304] = (a2[396] << 4) + a2[392];        // 高半字节 + 低半字节
if (a2[392] == 1) {  bit1 ← a2[356];  bit2 ← a2[360]; }
if (a2[392] == 2) {  bit0 ← a2[340];  bit3 ← a2[356];  bit4 ← a2[360]; }
```

`a2[392]` 即 `motion.enumSensorModeThis`，也就是 **`[304]` 的低 4 位**。
所以 `[311]` 的位只有在 `enumSensorMode ∈ {1,2}` 时才会被写入 ——
之前直接扫 `[311]` 八位毫无反应，是**测试条件错误**，不是字段无效。

### 13.4 写 `[304]` 非零会让设备 **USB 重枚举**

实测写 `[304]=1` 时第一个报告即返回 `ERROR_DEVICE_NOT_CONNECTED (0x48F)`，
随后设备从 **XInput 槽 0 跳到槽 1**，配置读回 `[304]=0`（模式位不持久）。

处理：
- `tools/xinput-sample.py` 已改为**自动探测 0..3 槽位**（默认不再写死 index 0）
- 该现象本身是「模式开关」的直接证据：设备确实会因 `sensorMode` 切换呈现方式

### 13.5 体感数据的出口：不在 HID 上

| 通道 | 结论 |
|---|---|
| `MI_00` 游戏报告（14B） | 摇杆固定时仅 `[4]`/`[6]` 抖动，**无 6 个陀螺通道** |
| `MI_01 / 0xFFB1` 厂商页 | 只有输出端点，`read()` 直接报错，**读不到** |
| `MI_01 / 0x000C` | 消费类控制页（多媒体键） |

推论（待验证，用户提出、与三处证据一致）：
**陀螺仪在设备内部直接映射到摇杆输出**，主机侧拿不到原始角速度。
体感块 `[304..311]` 只是这套映射的**设置**，不是数据通道。

因此测 `gyro_sens / h2v_ratio / resp_curve / deadzone_comp` 的唯一途径是：
**转动手柄 → 观察右（或左）摇杆读数**，与摇杆曲线同一套方法论。

## 14. 体感页三项设置的真机解码（第五轮，官方 UI 对照）

方法：在官方软件里改一项 → 读回 508B 全量 diff。每轮只动一个设置，diff 结果即该设置的字节。

### 14.1 `[304]` = 高半字节(响应方式) + 低半字节(模拟摇杆)

| 官方 UI 设置 | `[304]` | 说明 |
|---|---|---|
| 关闭 | `0x00` | 实测 LY 立即归中（82），摇杆不被接管 |
| 模拟左摇杆 + 常开 | `0x01` | 实测 LY 立即打满 32767 |
| 模拟左摇杆 + 触发按键(A) | `0x11` | 高半字节 0→1 |
| 模拟右摇杆 | `0x02` | 反编译枚举（`enumSensorMode == 2`），真机未验证 |

```
[304] = (响应方式 << 4) | 模拟摇杆选择
 响应方式:   0 = 常开,  1 = 触发按键
 模拟摇杆:   0 = 关闭,  1 = 模拟左摇杆,  2 = 模拟右摇杆（2 为反编译枚举，未真机验证）
```

与反编译一致：`a3[304] = (a2[396] << 4) + a2[392]`，其中 a2[392]=enumSensorModeThis（低半字节）。

### 14.2 `[305..308]` = sim_keys 位图（dword LE），枚举表见反编译

「响应方式 = 触发按键」并选 A 键时，**只有 `[308]` 从 0 变 1**，即 dword 位 24（`0x01000000`）。
反编译 `switch` 给出完整枚举（`case n → 位掩码`）：

| 枚举 | 掩码 | 位 | 枚举 | 掩码 | 位 |
|---|---|---|---|---|---|
| 0 | `0x40` | 6 | 11 | `0x4000000` | 26 |
| 1 | `0x100` | 8 | 12 | `0x10000` | 16 |
| 2 | `0x80` | 7 | 13 | `0x20000` | 17 |
| 3 | `0x200` | 9 | 14 | `0x40000` | 18 |
| 4 | `0x1` | 0 | 15 | `0x80000` | 19 |
| 5 | `0x2` | 1 | 16 | `0x2000` | 13 |
| 6 | `0x8` | 3 | 17 | `0x4000` | 14 |
| 7 | `0x10` | 4 | 18 | `0x8000` | 15 |
| 8 | `0x800000` | 23 | 19 | `0x400` | 10 |
| 9 | **`0x1000000`** | **24** | 20 | `0x800` | 11 |
| 10 | `0x2000000` | 25 | | | |

**A 键 = 枚举 9 = bit24**（真机已验证）。其余枚举项与具体按键名的对应关系尚未逐个验证，
需在官方 UI 里逐个选择并 diff（每项约 10 秒）。

`[305..308]` 是 dword **小端**，所以 bit24 落在 `[308]` 的最低位，与实测一致。

### 14.3 注意：四个体感参数在本机型**不生效**（写入即存、固件不消费）

`gyro_sens(316) / h2v_ratio(315) / resp_curve(318) / deadzone_comp(312)`：

| 验证项 | 结果 |
|---|---|
| 写入落盘 | 全部落盘（`316=0/20`、`315=0`、`318=0`、`312=50` 均读回一致） |
| 实时效果 | 无效果：`[316]` 取 0/10/20/40/60，`\|LX\|` 恒为 32767，零差异 |
| 重启后效果 | 无效果：写 `[316]=0` 后关机再开机（配置跨重启保住），仍然 `\|LX\|=32767` |
| 官方 UI 入口 | 无效果：体感页只有「模拟摇杆 / 响应方式 / 轴向反转」三项，**没有灵敏度滑块** |

结论：`config.xml` 是**跨机型通用 schema**，四个 profile 都挂着这 4 个属性，但本机型
（413D:2104）的 UI 从未提供入口，固件也不读。官方软件只是在 Implant 时把默认值
（60/10/42/0）写进 508B 而已。

**产品含义**：网页版体感页**不应展示这 4 个滑块**，否则用户调了没反应。若要保留，
必须标注「本机型固件不生效」。这与 `[304]` 形成鲜明对比 —— 后者改完 150ms 内立刻生效。

### 14.4 体感→摇杆的实际驱动方式：**重力/倾角，非角速度**

| 姿态 | LX | LY |
|---|---|---|
| 平放桌面（不动） | −1.1%（抖动 ±22） | 0.7% |
| 立起来（不动） | ≈0 | **32767 饱和** |
| 立着左右转动 | **−32767 … +32475 满量程摆动** | 32767（恒定） |

即：**侧倾(roll) → X，俯仰(pitch) → Y**，等价于把手柄当方向盘用，增益固定。
这也解释了 `gyro_sens` 为何无效 —— 该名称是角速度灵敏度，而这条路径根本不用角速度。

## 15. `[311]` 轴向反转位：bit1 = X，bit2 = Y（第六轮，垫物固定倾角）

### 15.1 方法（本轮与前几轮的关键差异）

前几轮的姿态都是**手持**，微小手抖会伪装成参数生效。本轮手柄**用物体垫住**，两轮之间
`LX/LY` 漂移 ≤ 14 计数（阈值 900），数据可作差。

流程（`tools/axis-invert-test.mjs`）：

1. 读回 508B，记 `[304]`、`[311]` 原值
2. **临时把 `[304]` 高半字节清 0**（`0x11 → 0x01`）。「按下触发」模式下静止不按键时
   体感根本没有输出，不先改这一位就什么也测不到。写完 `[304]` 设备会重枚举，等 2s
3. 每档 `settle 900ms` 后采 1.5s，**两轮取中位**（曲线类参数有数百毫秒过渡态，见 §11）
4. 结束把 `[311]` 与整份原始载荷写回，`[304]` 还原成用户设的 `0x11`

### 15.2 姿态 A：只侧倾（roll≈大，pitch≈0）

| 条件 | LX | LY | RX | RY |
|---|---|---|---|---|
| `[304]=0`（体感关，对照） | **−367** | 322 | 11 | −505 |
| `[311]=0x00`（基线） | −11667 | 322 | 7 | −511 |
| `[311]=0x02`（bit1） | **+10933** | 322 | 9 | −511 |
| `[311]=0x04`（bit2） | −11681 | 322 | 9 | −504 |
| `[311]=0x06`（bit1+2） | **+10941** | 322 | 9 | −506 |

### 15.3 姿态 B：只俯仰（pitch≈30°，roll≈0）

| 条件 | LX | LY |
|---|---|---|
| `[311]=0x00`（基线） | −234 | **+16970** |
| `[311]=0x02`（bit1） | −234 | +16970 |
| `[311]=0x04`（bit2） | −234 | **−16938** |
| `[311]=0x06`（bit1+2） | −234 | −16926 |

### 15.4 结论

```
[311] bit1 = 体感 X（水平）反转
[311] bit2 = 体感 Y（垂直）反转
两位互相独立，可任意组合；均作用于「体感分量」，不是物理摇杆
```

三条由数据直接支撑的推论：

1. **体感驱动的是左摇杆完整 XY**，不是只有 X。姿态 A 下 `motion_Y=0`（LY 恒 322），
   姿态 B 下 `motion_X=0`（LX 恒 −234），所以两个姿态互为对方的空白对照 —— 这也说明
   单轴测试**必须挑该轴分量非零的姿态**，否则「位无效」是假阴性。
2. **体感输出是叠加在摇杆自身轴值上**，不是覆盖。姿态 A 里 `−11667 → +10933` 差 734
   计数，恰好等于 `2 × 367`（体感关时的摇杆静态偏移 `−367`）；扣掉它，体感分量是
   `−11300 → +11300`，纯取反、零非线性。**不要把这个 6.4% 的幅度差解读为曲线不对称。**
3. **`[311]` 与 `[13]` 是两条互不相干的反转路径**：`[13]` bit0/1、bit4/5 反转的是
   物理摇杆轴（§13），`[311]` bit1/2 反转的是体感合成的分量。体感页的「轴向反转」
   复选框写的是后者。

### 15.5 仍未定

- `[311]` bit0：两个姿态下清零均无差异，语义未定
- **`[311]` 的位布局随 `[304]` 低半字节切换**（反编译 §13.3）：mode 1 → X=bit1 / Y=bit2（真机已验证）；
  mode 2 → X=bit3 / Y=bit4（另有 bit0 ← `a2[340]`，语义未定）。网页版已按此分派。
- `[304]` 低半字节 = 2（模拟右摇杆）尚未上真机：写入值与读回一致，但倾角是否真的驱动右摇杆、
  `[311]` bit3/bit4 在真机上是否按反编译那样生效，都还没测。
